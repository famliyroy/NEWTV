## 1. 一句话结论

这不是一个"前端项目 + 后端 API"的分离架构，而是一个 **Next.js 14 App Router 全栈单体**：页面、251 个 API 路由、数据访问层、爬虫聚合器、Socket.IO 实时服务全部在同一个 Node 进程里。它**没有独立后端服务**，所谓"后端"就是它自己起的那个 HTTP 服务器。

这决定了打包策略：**不是把后端"拆出来"，而是把整个运行时"装进去"。**

## 2. 运行时拓扑

```
┌──────────────────────────────────────────────────────────────┐
│  浏览器 / WebView / Electron Renderer（客户端）               │
│  React 18 · ArtPlayer · hls.js · flv.js · anime4k(WebGPU)     │
│  public/libbitsub/（位图字幕 ESM） · next-pwa Service Worker  │
│  IndexedDB / localStorage（localstorage 模式下是唯一存储）    │
└───────────────┬──────────────────────────┬───────────────────┘
                │ HTTP (fetch / RSC)       │ WebSocket
┌───────────────▼──────────────────────────▼───────────────────┐
│  Node 进程（server.js，自定义 Next 服务器）                    │
│  ├─ Next request handler（页面 + 251 个 route handler）        │
│  ├─ Socket.IO：观影室同步 / TV 遥控（tv-remote-hub.js）        │
│  ├─ middleware.ts：PASSWORD 校验 / TV 模式开关                │
│  └─ 存储抽象 db.ts ──┬─ d1 分支 → better-sqlite3（本地文件）   │
│                      ├─ redis / kvrocks / upstash             │
│                      └─ turso(libSQL) / postgres              │
└───────────────┬──────────────────────────────────────────────┘
                │ 出站 HTTPS
┌───────────────▼──────────────────────────────────────────────┐
│  外部依赖：苹果CMS V10 资源站 · 豆瓣 · TMDB · Bangumi ·        │
│  弹幕 API · 网盘(OpenList/小雅) · Emby · TTS · Telegram ·     │
│  邮件 SMTP · Web Push(FCM)                                    │
└──────────────────────────────────────────────────────────────┘
```

关键点：**出站依赖极多，且全部由服务端代理转发**（`/api/proxy/*`、`/api/image-proxy`、`/api/video-proxy`）。这是打包后仍必须保留完整 Node 运行时的根本原因——把这些逻辑搬到浏览器端会撞 CORS、Referer 校验、SSRF 防护。

## 5. 构建与启动链路（打包的"施工图"）

### 5.1 构建

```
pnpm gen:manifest            # scripts/generate-manifest.js → 写入版本/清单
  └─ next build              # next.config.js: output = 'standalone'
       └─ withPWA(nextConfig)   # 生产构建注入 Service Worker，dest=public
  └─ postbuild: echo ...
pnpm deploy --filter=. --prod --legacy /tmp/prod-deps   # 抽取生产 node_modules
```

要点：
- `output: 'standalone'` 只在非边缘构建生效（`CF_PAGES` / `BUILD_TARGET=cloudflare|edgeone` 时关闭）。
- **standalone 产物不含 `public/` 与 `.next/static/`**，也不含 `migrations/`、`scripts/`、根 `server.js`、`src/lib/tv-remote-hub.js`。Dockerfile 正在逐个 `COPY` 补齐——这份清单就是打包清单，可直接抄。
- `next-pwa` 会往 `public/` 写 `sw.js` / `workbox-*.js` / `push-sw.js`，`skipWaiting: true`。

### 5.2 启动

```
node start.js
  ├─ generateManifest()
  ├─ require('./server.js')
  │    ├─ ensureSQLiteReady()  # 当 STORAGE_TYPE=d1 且非 CF → init-sqlite.js 建库跑迁移
  │    ├─ next({ dev, hostname: HOSTNAME||0.0.0.0, port: PORT||3000 })
  │    └─ http.createServer + Socket.IO（观影室、TV 遥控）
  └─ 轮询 http://HOSTNAME:PORT/login → 通后每 3600s 调 /api/cron/<CRON_PASSWORD>
```

### 5.3 容器内环境基线

| 变量 | 容器值 | 打包时应改为 |
| --- | --- | --- |
| `NODE_ENV` | production | production |
| `HOSTNAME` | `0.0.0.0` | **`127.0.0.1`**（桌面端不得暴露局域网） |
| `PORT` | `3000` | 动态选端口 |
| `SQLITE_DB_PATH` | `/app/.data/moontv.db` | 用户数据目录（如 `%APPDATA%\MoonTVPlus\data\moontv.db`） |
| `OFFLINE_DOWNLOAD_DIR` | `/data` | 用户视频目录 |
| `DOCKER_ENV` | true | 建议保持 true（走容器等价路径） |

## 6. 数据层：7 种后端，只有 1 种能离线

`src/lib/db.ts` 用 `NEXT_PUBLIC_STORAGE_TYPE` 工厂分发：

| 取值 | 实现 | 依赖 | 能否离线自包含 |
| --- | --- | --- | --- |
| `localstorage` | 浏览器 localStorage | 无 | 仅客户端态；middleware 直接比对 `PASSWORD` |
| `d1` | `D1Storage` + `d1-adapter` | **better-sqlite3**（原生） | **能，这是桌面/离线唯一正解** |
| `turso` | `TursoStorage` | `@libsql/client`（含原生） | 否，需远程 |
| `redis` / `kvrocks` / `upstash` | 各自实现 | `redis` 客户端 / HTTP | 否，需远程 |
| `postgres` | `PostgresStorage` | `@vercel/postgres` / `pg` | 否，需远程 |

SQLite 路径解析（`scripts/init-sqlite.js`）：

```
SQLITE_DB_PATH || path.join(process.cwd(), '.data', 'moontv.db')
pragma: journal_mode=WAL, foreign_keys=ON, busy_timeout=5000
迁移：migrations/*.sql 按文件名排序执行；baseline 截断在 008，008 之后为增量
错误容忍：table/index already exists、duplicate column name 视为可忽略
```

数据文件是 3 个（`.db` / `-wal` / `-shm`），备份与迁移必须整组拷贝。

## 7. 鉴权与中间件（打包时必须注入的配置）

`src/middleware.ts` 的执行顺序决定了"装完打不开"的典型故障：

1. `ENABLE_TV_MODE=false` → `/tv` 直接 404。
2. 跳过白名单路径（登录、静态资源等）。
3. **`process.env.PASSWORD` 为空 → 全站重定向 `/warning`**。这是打包后白屏/跳警告页的第一大原因。
4. `localstorage` 模式：Cookie 内密码与 env 直接比对。
5. 其他模式：校验 `username / role / signature / timestamp`，支持续期与 token 失效。

结论：安装器/首启向导**必须**生成并写入 `USERNAME` + `PASSWORD`（随机 16 位），否则应用起来就是警告页。

## 10. 客户端可行性评级（原生客户端模式）

前提：后端已在自有服务器常驻运行（Docker + kvrocks + HTTPS 反代），**客户端自己实现界面，通过 HTTP 调用后端 API**，后端零改动。

| 目标形态 | 技术路线 | 可行性 | 主要代价 | 判定 |
| --- | --- | --- | --- | --- |
| **Windows + Android 双端** | **Flutter + media_kit**（同套代码） | **高（85%）** | 包体 45–60 MB（Win）/ 28–38 MB（APK）；工期 48.5 人日 | **v1 采用** |
| Windows EXE | Tauri 2 壳 → 加载远程地址 | 很高（95%） | 包体 6–12 MB；但**无法复刻界面、无法改弹幕** | **已否决** |
| Android APK | 复用 `apps/android-tv` 壳 → 手机竖屏 + 地址配置 | 很高（95%） | 同样无法改前端行为 | **已否决** |
| 双原生（WinUI + Compose） | 各写一套 | 中（60%） | 工作量 ×2，维护双倍 | 不选 |
| 离线自包含（任一端） | 内嵌 Node + standalone | 低（30%） | 需重编原生模块；8–12 周 | **不做**，已有服务端 |

**否决薄壳的原因（重要，避免反复）**：NipaPlay 风格 UI 与"弹幕全自动加载"都是**前端行为**。薄壳里前端跑在服务器上，要不改后端就只能放弃这两个需求。主人明确要求这两个需求，所以必须原生。

**可行性 85% 而非 95% 的扣分项**：`media_kit` 在 Android 部分机型的硬解兼容、HLS 分片重定向、以及弹幕渲染的性能上限，是三个需要在 M2 前用原型验证的技术点（见 `03` T-3.1 / T-4.3）。

## 11. 打包必须遵守的 12 条硬约束

> **适用范围**：仅当要做「内嵌引擎的离线自托管版」时成立。
> **当前远程后端方案不涉及**（客户端不含任何 Next 产物），本节保留是为了将来做离线版时不必重新踩坑。
> 任何一条被忽略都会导致"构建成功但装上打不开"。

1. **standalone 的 `server.js` 与仓库根 `server.js` 同名**：先拷 standalone，再用项目根 `server.js` 覆盖，否则丢失 Socket.IO。
2. `src/lib/tv-remote-hub.js` 不被 Next 追踪，必须手动拷贝（Dockerfile 有注释佐证）。
3. `public/` 与 `.next/static/`必须手动拷贝，否则页面无样式。
4. `migrations/` 与 `scripts/init-sqlite.js` 必须随包，否则首次启动建库失败。
5. `better-sqlite3` 的 ABI 必须与运行它的 Node 一致 → 优先"独立 node 可执行文件"，而不是 Electron 内置 Node。
6. `HOSTNAME` 必须改为 `127.0.0.1`，不得 `0.0.0.0`。
7. `SQLITE_DB_PATH` 必须指向用户可写目录，不能指向 `Program Files`。
8. `PASSWORD` 必须非空，否则全站跳 `/warning`。
9. 页面必须通过 `http://127.0.0.1:<port>` 加载，**不能用 `file://`** —— WebGPU / 剪贴板 / Service Worker 等能力要求安全上下文，`localhost` 与 `127.0.0.1` 被浏览器视为安全源。
10. `next-pwa` 的 SW 在 WebView/Tauri 内行为不一致，需按端关闭或加版本失效策略。
11. 端口必须动态探测（3000 常被占用），并在渲染进程加载前完成健康检查。
12. Socket.IO 依赖长连接，Android 后台会被系统挂起 → 需前台服务或降级提示。

## 12. 风险前置结论（详见 04 文档）

- **技术侧**：原生客户端已消除打包类风险，风险转移到三处——**鉴权令牌链路**（Cookie + HMAC + 双令牌，实现错了全线 401）、**弹幕多源聚合**（后端只给单源，聚合要在客户端写）、**播放内核兼容**（media_kit 硬解与 HLS 重定向）。
- **法务侧**：仓库 `LICENSE` 正文为 **CC BY-NC-SA 4.0**（非商业 + 相同方式共享），而 README 标注 **MIT** —— 二者冲突。客户端不修改上游、不构成衍生作品，但**仍须署名**；引用上游图标/文案时受 NC + SA 约束。参考项目 NipaPlay-Reload 为 **MIT**，可直接读码，但须保留版权声明。
- **隐私侧**：客户端默认地址若写死并公开，等于公开私人站点。处理方式见 `02` 第 8 节（S1 硬约束）。

## 13. 客户端必须对接的接口契约

> 本节是**实现方唯一的接口依据**。字段名取自源码类型定义（`src/lib/types.ts`、`src/lib/danmaku/types.ts`）。
> **但字段以真实响应为准**：`03` 的 T-0.2 要求用真实账号抓一次响应存成 fixture，与本节对照补全，冲突时以真实响应为准并回写本节。

### 13.1 通用约定

| 项 | 约定 |
|---|---|
| Base | 用户填写的服务器根地址（`https://xxx`，无尾斜杠） |
| 编码 | 请求/响应均 JSON（弹幕代理例外，见 13.5） |
| 鉴权 | Cookie `auth`（HMAC 签名 JSON），非 Bearer |
| 未登录 | API 返回 **401**（不是 302；只有页面请求才 302 跳登录） |
| 令牌过期 | 401 且文本 `Access token expired` → 可调 refresh |
| 刷新令牌过期 | 401 → **必须重新登录** |
| 限流 | 登录失败有 fail2ban，可能返回 **429** |

### 13.2 认证

```
POST /api/login
  body: { "password": "...", "username": "..."? }   // username 仅非 localstorage 模式需要
  200:  { "ok": true, "token"?: "...", "auth"?: {...} }
        Set-Cookie: auth=<signed>
  401:  密码错误
  429:  失败次数过多

POST /api/auth/refresh
  cookie: auth
  200:  新 Set-Cookie: auth（新 accessToken）
  401:  需重新登录

POST /api/logout
  200:  清 cookie
```

**关键实现点（`middleware.ts` 逻辑还原）**

- cookie 必须整体持久化；只存 `token` 字段会导致所有接口 401
- 判定顺序：无 cookie → 401；`refreshExpires` 过期 → 401（重登）；`timestamp` 超龄 → 401 `Access token expired`（可 refresh）；签名不匹配 → 401
- 并发 401 必须**单飞 refresh**（`03` T-1.2 验收项）

### 13.5 播放（免鉴权，本项目关键便利）

```
GET /api/proxy-m3u8
    ?url={encodeComponent(原始播放地址)}
    &source={sourceCode}
    [&token=...]            // 仅当服务端设了 NEXT_PUBLIC_PROXY_M3U8_TOKEN
    [&adblock=false]        // 默认 true，服务端做广告分片过滤
    [&proxySegments=true]   // 默认 false，开启后所有 ts 分片也走代理（流量翻倍）
  200: m3u8 文本
  401: 设置了播放令牌但 token 不匹配
  400: 缺 url
```

**为什么这条特别重要**：`middleware` 的 matcher 明确排除了 `api/proxy-m3u8`，即**不需要登录**。播放内核（libmpv）发起的 HLS 请求天然带不上客户端 cookie，若该接口要鉴权就必须给内核注入 header，而 HLS 分片重定向极易丢 header。现在只需把完整代理 URL 交给内核。

### 13.6 弹幕（四接口，弹幕自动化全部基于它们）

```
GET  /api/danmaku/search?keyword={标题}
     → { errorCode, success, errorMessage, animes: DanmakuAnime[] }
       DanmakuAnime = { animeId, animeTitle, type, typeDescription,
                        imageUrl?, startDate?, episodeCount?, rating?, source, links? }

POST /api/danmaku/match           body: { "fileName": "..." }
     → { errorCode, success, isMatched, matches: [...] }   // 结构不稳定，需防御

GET  /api/danmaku/episodes?animeId={id}
     → { bangumi: { bangumiId, animeTitle, episodes: [{ episodeId, episodeTitle }] } }
       ★ 注意：episode 只有 episodeId 与 episodeTitle，**没有集号字段**
         → 集数匹配只能解析标题，算法见 06 第 5 节

GET  /api/danmaku/comment?episodeId={id}
     → { count, comments: [{ p, m, cid }] }
       p = "时间,类型,字体大小,颜色,时间戳,弹幕池,用户Hash,弹幕ID"
       m = 文本
```

**上游实现的三个缺陷（正是"必须手动选源"的根因）**

1. `comment/route.ts` 把上游 URL 写死为 `?format=xml`，**单集单源**
2. **没有**传 `withRelated=true`，弹幕服务端支持的关联源聚合能力被丢弃
3. 交互层把"自动加载失败"直接交给用户手动选，没有多源并行尝试

> 客户端方案：**完全绕开这三个缺陷**，自己实现"多源发现 → 集数匹配 → 并发拉取 → 合并去重"。详见 `06`。
> 内置公共弹幕源 `mtvpls-danmu.netlify.app` 实测返回 **503 已不可用**，因此弹幕可用性取决于服务端 `SiteConfig.DanmakuApiBase` 指向的服务。
