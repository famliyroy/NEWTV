# 06 - 弹幕全自动加载技术方案

> 需求原话：**"弹幕功能我希望把所有收集到的都自动加载，不需要用户点击选择"**
>
> 本文是这个需求从"现状"到"可交付"的完整技术方案。阅读对象：实现弹幕模块的开发者/AI。
> 前置阅读：`01-逆向分析报告.md` 第 7 节（鉴权）、第 12 节（弹幕链路缺陷）。

---

## 1. 现状：为什么现在必须点击

上游 MoonTVPlus 的弹幕链路是**四步手动流程**：

| 步骤 | 用户动作 | 调用 |
|---|---|---|
| 1 | 打开弹幕面板 | — |
| 2 | 输入/确认关键词 | `GET /api/danmaku/search?keyword=` |
| 3 | 从多个"番剧条目"里挑一个 | `GET /api/danmaku/episodes?animeId=` |
| 4 | 从剧集列表里挑一集 | `GET /api/danmaku/comment?episodeId=` |

代码证据（`src/app/play/page.tsx`）：`setShowDanmakuSourceSelector(true)` 只在自动匹配失败或用户手动触发时调用；自动加载函数 `loadDanmakuForCurrentEpisode` 命中失败后就停在"等用户选"的状态。

**根因不在交互层，在数据层：**

`src/app/api/danmaku/comment/route.ts` 第 66-73 行把上游 URL 写死成：

```ts
apiUrl = `${baseUrl}/api/v2/comment/${episodeId}?format=xml`;
```

- 只接受**单个** `episodeId` → 一次只能拿**一个来源**的弹幕
- **没有**带 `withRelated=true` → 弹幕服务端支持的"同剧集关联源聚合"能力被丢掉了
- `format=xml` 后用正则解析 `<d p="...">text</d>`，一次请求只能覆盖一个 provider

而弹幕服务（danmu_api 兼容实现）本身是**支持多源**的：按标题搜索时，同一部番会返回**多个 anime 条目**（B站/巴哈/腾讯/爱奇艺等，实测同一部番最多看到 11 个来源），每个条目下各有一份 episodeId，各自挂着独立的弹幕池。

> **结论：要"全部自动加载"，缺的不是开关，是"多源发现 + 并发拉取 + 合并"这一层。这一层必须自己写。**

## 2. 两个可选实现位置

| | 方案 A：客户端聚合（推荐） | 方案 B：服务端聚合 |
|---|---|---|
| 改动位置 | Flutter 客户端新增 `DanmakuAggregator` | 改 `comment/route.ts` 支持 `episodeIds=a,b,c` + `withRelated=true` |
| 是否要动后端 | **否，线上实例零改动** | **要**，需重新构建镜像并重部署 |
| 生效范围 | 只有新客户端受益 | 所有端（含网页版）受益 |
| 失败影响面 | 只影响客户端自身 | 改坏了全站弹幕都挂 |
| 工作量 | 3 人日 | +2 人日（含回归）+ 部署窗口 |
| 风险 | 客户端请求数变多（N 个源 = N 次请求） | 单次请求变重，服务端 120s 超时可能被打满 |

**决策：v1 走方案 A，不碰后端。**

理由：客户端是新建项目，本来就要写网络层；后端是主人已经部署好的线上实例，为一个小功能引入重部署风险不划算。方案 B 留作 v2 优化项（见第 10 节），等客户端验证了"多源聚合确实有收益"再考虑把合并逻辑下沉。

## 3. 数据流：全自动 6 步

```
进入播放页
  │
  ├─① 取上下文：作品标题 + 集号 + 备用关键词
  │    来源：/api/detail 返回的 vod_name / episodes_titles[当前序号]
  │
  ├─② 多源发现：GET /api/danmaku/search?keyword={标题}
  │    → animes[]  一次拿到所有来源的同名条目（通常 3~11 个）
  │
  ├─③ 逐源取剧集：GET /api/danmaku/episodes?animeId={id}   （并发，N 个）
  │    → bangumi.episodes[] = [{episodeId, episodeTitle}]
  │
  ├─④ 集数匹配：把"要看的第 k 集"映射到每个源的 episodeId
  │    匹配不上 → 该源跳过（不阻塞其它源）
  │
  ├─⑤ 并发拉弹幕：GET /api/danmaku/comment?episodeId={id}  （并发，限 6）
  │    → {comments:[{p:"时间,类型,字体,颜色,...", m:"文本"}]}
  │
  ├─⑥ 合并去重 → 按时间排序 → 写入本地缓存 → 交给播放器渲染
  │
  └─ 全程无用户交互；屏幕上只出现一个不可点击的进度角标："弹幕 3/7 源 · 4218 条"
```

**关键设计：弹幕加载与视频播放并行，绝不阻塞起播。** 视频 `play()` 在前，弹幕在后台补齐，加载完成时若播放进度已在 30s 内，则立即开始滚动（不回溯）；超过 30s 则从当前位置开始渲染，避免"一开弹幕满屏糊脸"。

## 4. 第 ③ 步：多源发现的两个入口

### 4.1 主路径：标题搜索

```dart
GET /api/danmaku/search?keyword={urlEncode(标题)}
→ {
    "errorCode": 0, "success": true,
    "animes": [
      { "animeId": 10357, "animeTitle": "葬送的芙莉莲", "type": "tvseries",
        "source": "哔哩哔哩", "episodeCount": 28, "imageUrl": "...", "startDate": "2023-09-29" }
    ]
  }
```

**标题清洗规则**（决定召回率，务必照做）：

```
原始: "葬送的芙莉莲[简中][1080P]"   → 关键词: "葬送的芙莉莲"
原始: "【喵萌奶茶屋】葬送的芙莉莲 - 01" → 关键词: "葬送的芙莉莲"
```

1. 去掉方括号/圆括号包裹的内容（`[]`、`（）`、`()`、`【】`）
2. 去掉分辨率与编码标记：`1080P|720P|2160P|4K|HEVC|x264|x265|AVC|WEB-DL|BluRay`
3. 去掉字幕组常见后缀：`简中|繁中|简繁|字幕组|喵萌|LoliHouse|ANi|桜都`
4. 去掉集号片段：`- 01`、`第01话`、`EP01`
5. 结果若为空，回退用原标题；若仍为空，放弃弹幕（静默）

### 4.2 兜底路径：文件名匹配

当标题搜索返回 `animes` 为空时，若可拿到视频文件名或 URL：

```dart
POST /api/danmaku/match  body: {"fileName": "..."}
→ { "matches": [{ "episodeId":..., "animeTitle":..., }], "isMatched": true }
```

> 注意：`match` 是"尽力而为"接口，返回结构在不同 danmu_api 实现下不完全一致，**必须做字段防御**（`matches` 可能为 null）。

### 4.3 弹幕源可用性前提（必须写进首次启动向导）

`getDanmakuApiBaseUrl(config.SiteConfig)` 的逻辑：

- `DanmakuSourceType === 'builtin'` → 固定 `https://mtvpls-danmu.netlify.app/87654321`
- 否则 → `DanmakuApiBase`（可加 `/token` 后缀）

**实测：内置公共源已返回 503，不可用。** 因此客户端文档必须明确告知用户"弹幕需要后端配置一个可用的弹幕服务"，并在弹幕功能首次失败时给出可操作的提示文案，而不是静默空白（见第 8 节降级策略）。

## 5. 第 ④ 步：集数匹配算法（最易出错，单独成节）

问题：`DanmakuEpisode` 只有 `episodeId` 和 `episodeTitle`，**没有 episodeNumber 字段**。所以只能从标题里解析集号。

```dart
/// 从剧集标题 / 从播放器上下文解析出整数集号，失败返回 null
int? parseEpisodeNumber(String text) {
  // 1) 中文序号：第12话 / 第12集 / 第十二话
  // 2) 英文：EP12 / E12 / Episode 12
  // 3) 裸数字：单独出现的 1~4 位数字（排除年份 19xx/20xx）
  // 4) 小数集：12.5（.5 特殊集）
}
```

匹配优先级（命中即停）：

| 优先级 | 规则 | 说明 |
|---|---|---|
| P0 | 用户/详情页已知的集号 == 解析出的集号 | 正常情况 |
| P1 | 剧场版/OVA：标题含 `剧场版|Movie|OVA|OAD` 且当前也是剧场版 | 单集作品直接取 `episodes[0]` |
| P2 | 源剧集数量 == 详情页剧集数量，取数组同下标 | 剧集对齐但标题无集号时最可靠 |
| P3 | 解析失败但源只有 1 集 | 单集直接取 |
| P4 | 全部失败 | **跳过该源**，不猜 |

**硬性禁止**：不允许"随便取第一集"作为兜底。错集的弹幕比没有弹幕更糟——用户会看到完全无关的剧情。

## 6. 第 ⑥ 步：合并与去重

### 6.1 弹幕属性格式

`p` 字段是逗号分隔的 8 段（dandanplay 兼容格式）：

```
p = "时间,类型,字体大小,颜色,时间戳,弹幕池,用户Hash,弹幕ID"
例子: "12.345,1,25,16777215,1695555123,0,abc123,998877"
```

| 下标 | 含义 | 用途 |
|---|---|---|
| 0 | 出现时间（秒，浮点） | 排序、渲染时间轴 |
| 1 | 类型：`1`=滚动 `4`=底部 `5`=顶部 | 映射到渲染模式 |
| 2 | 字号 | 一般忽略，用全局设置 |
| 3 | 颜色（十进制 RGB） | `#${value.toRadixString(16).padLeft(6,'0')}` |
| 7 | 弹幕 ID | **跨源不可比，不能当去重键** |

### 6.2 去重键

不同源的同一句弹幕，`时间戳`、`用户Hash`、`ID` 全都不一样，唯一稳定的是**内容 + 时间**：

```dart
String dedupKey(DanmakuComment c) {
  final t = (double.parse(c.p.split(',')[0]) * 10).round(); // 0.1s 精度
  final text = c.m.replaceAll(RegExp(r'\s+'), '');          // 去空白
  return '$t|$text';
}
```

- **0.1s 精度**：同一句弹幕在不同源的入库时间可能有 ±0.2s 抖动，用整秒会误合并、用毫秒会漏合并，0.1s 是实测折中。
- 冲突时**保留先到者**，但若先到者是默认白色（`16777215`）而后来者有颜色，**继承颜色**（彩色的信息量更大）。

### 6.3 排序与索引

合并后按时间升序排列，构建 `List<double> timeline`，渲染时用二分查找定位 `[currentTime, currentTime+8s]` 窗口内的弹幕。**不要每帧遍历全量列表**——12000 条弹幕 × 60fps 会直接掉帧。

## 7. 性能预算：必须设上限

实测单集最多约 6600 条；11 个源理论上能到 7 万条。**必须限流，否则内存和渲染都会崩。**

| 约束 | 值 | 理由 |
|---|---|---|
| 并发请求数 | **6** | 再多会被源站限流/丢包 |
| 单源超时 | **8 s** | 超时即放弃该源，不重试（避免拖慢整体） |
| 整体预算 | **12 s** | 超过则停止等待，用已到的结果先渲染 |
| 单源条数上限 | **3000** | 超出按时间均匀抽样，保留首尾（开头结尾弹幕最密集） |
| 合并后总上限 | **12000** | 超出后按 3000/源 比例二次抽样 |
| 渲染同屏上限 | **80 条** | 超出按轨道淘汰，防糊屏 |
| 缓存 TTL | **7 天** | 按 `标题+集号` 存 SQLite |

**抽样要保留语义**：均匀抽样会打散"名场面刷屏"的密度感。优先策略是**按源分配配额**（每个源至少保 300 条，剩余配额按源的历史命中率分配），而不是全局均匀抽。

## 8. 降级策略（决定"看起来像不像成品"）

| 场景 | 表现 | 文案 |
|---|---|---|
| 后端未配弹幕源（503） | 播放器右下角弹幕按钮置灰，长按显示原因 | "服务端未配置可用弹幕源" |
| 搜索到 0 个源 | 角标显示"无弹幕"，不弹窗、不打断 | "未找到该作品的弹幕" |
| 部分源超时 | 正常渲染已到的源，角标写"N/M 源" | — |
| 全部源失败 | 静默，只记本地日志 | — |
| 离线 | 用本地缓存；无缓存则静默 | — |

**原则：弹幕是增强功能，任何情况下都不能阻断播放、不能弹模态对话框。**

## 9. 验收标准（可测，逐条打勾）

| # | 验收项 | 通过条件 |
|---|---|---|
| A1 | 零点击 | 进入播放页后不做任何操作，弹幕自动出现 |
| A2 | 多源生效 | 同一作品，日志中成功拉取的源数 ≥ 2 |
| A3 | 去重正确 | 抽样 100 条，跨源重复率 < 3% |
| A4 | 集数正确 | 抽查 10 部作品 × 3 集，弹幕内容与剧情一致（人工） |
| A5 | 不阻塞起播 | 视频首帧时间与关闭弹幕时相比，差值 < 200 ms |
| A6 | 性能 | 12000 条弹幕下，播放 60fps 不掉帧（Android 中端机 ≥ 50fps） |
| A7 | 超时降级 | 断掉弹幕源网络，播放页 12s 内正常可用，无白屏/无弹窗 |
| A8 | 缓存命中 | 二次进入同一集，弹幕出现时间 < 500 ms |
| A9 | 记忆 | 手动改过源的剧集，下次仍用用户选择（记忆优先于自动） |
| A10 | 关闭开关 | 全局关闭弹幕后，不发任何弹幕请求（省流量） |

## 10. v2 可选优化：把合并下沉到服务端

当且仅当满足以下条件时再做：
- 方案 A 已验证多源聚合确实显著提升体验（A2/A3 达标）
- 主人接受一次服务端重部署

改动点（`src/app/api/danmaku/comment/route.ts`）：

```ts
// 支持批量 + 关联聚合
const episodeIds = searchParams.get('episodeIds');   // "10357,20412,..."
apiUrl = `${baseUrl}/api/v2/comment/${episodeId}?format=xml&withRelated=true`;
```

配合客户端只发 1 次请求。**收益**：请求数从 N 降到 1，弱网体验更好。**代价**：服务端 120s 超时可能被大请求打满，需要加并发限流与结果缓存。

`withRelated=true` 的实际增益**必须实测**后再决定是否启用——文档不预设它一定有效。
