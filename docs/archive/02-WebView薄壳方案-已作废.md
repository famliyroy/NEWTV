# 客户端打包方案（远程后端模式）

> **本文取代归档中的「内嵌引擎方案」。**
> 前提变更：MoonTVPlus 已在自有服务器上以 Docker 常驻运行，客户端不需要自带任何后端、数据库或 Node 运行时。
> 客户端要做的事只有一件：**以原生应用的外壳，托管那个已经在跑的 Web 服务。**

---

## 1. 架构

```
┌──────────────────── 客户端（薄壳，零业务逻辑） ────────────────────┐
│                                                                  │
│   Windows（Tauri 2）                 Android（原生 WebView 壳）   │
│   ├─ 主窗口 → 远程 URL               ├─ MainActivity → 远程 URL   │
│   ├─ 托盘 / 单实例 / 快捷键          ├─ 竖屏 / 返回键 / 全屏      │
│   ├─ 外链交系统浏览器                ├─ 系统下载器 / 通知          │
│   ├─ 下载 / 新窗口 / 权限钩子        ├─ Cookie 持久化             │
│   ├─ 设置页（地址 / 缓存 / 关于）    ├─ 配置页 + 扫码导入         │
│   └─ 更新检查（GitHub Release）      └─ 更新检查                  │
└──────────────────────────────┬───────────────────────────────────┘
                               │ HTTPS（唯一依赖）
┌──────────────────────────────▼───────────────────────────────────┐
│  nginx（Let's Encrypt）→ 127.0.0.1:3000                          │
│  moontv-core（Docker，ghcr.io/mtvpls/moontvplus）                │
│  moontv-kvrocks（存储：播放记录 / 收藏 / 用户 / 配置）            │
└──────────────────────────────────────────────────────────────────┘
```

一句话：**后端不动，客户端只做「壳 + 体验收口」。**

---

## 2. 线上实例事实（已实测核验）

| 项 | 实测结果 | 对客户端的意义 |
| --- | --- | --- |
| 服务进程 | 容器 `moontv-core`，镜像 `ghcr.io/mtvpls/moontvplus:latest` | 跟随上游镜像，客户端无需关心版本 |
| 监听 | `0.0.0.0:3000` → nginx 反代 `127.0.0.1:3000` | 客户端只认 443，不碰 3000 |
| 入口 | HTTPS / HTTP2，Let's Encrypt 证书（至 2026-12-31，自动续期） | **安全上下文成立** → WebGPU 超分、Service Worker、剪贴板全部可用 |
| 鉴权 | 匿名访问返回 `307 → /login` | 客户端必须容纳登录流程与 Cookie 持久化 |
| 存储 | 独立 `moontv-kvrocks` 容器 | 数据全在服务端，多端天然同步 |
| 站点配置 | `USERNAME` / `PASSWORD` / `NEXT_PUBLIC_STORAGE_TYPE` / `NEXT_PUBLIC_SITE_NAME` 均已设置 | 不需要任何本地初始化 |
| TV 模式 | 未显式关闭（默认启用） | `/tv` 路由可用，将来可扩 TV 版 |

> **HTTPS 这一项尤其关键**：上游明确「超分需非 HTTP 环境」。你们已是 TLS，桌面端与 Android 端都能吃到完整能力；若当初是裸 HTTP，WebGPU 与 PWA 都会瘸腿。

## 3. 为什么方案能简化一个数量级

| 原方案（内嵌引擎） | 现方案（远程客户端） |
| --- | --- |
| Electron + 内嵌 `node.exe` | Tauri 2（复用系统 WebView2） |
| 打包 Next standalone（~200 MB 依赖） | 零后端产物 |
| better-sqlite3 ABI 重编风险 | **不存在** |
| SQLite 建库 + 12 个迁移 | **不存在**，服务端 kvrocks |
| 首启生成账号密码 | 直接登录服务器账号 |
| 端口冲突 / 进程回收 / 崩溃域 | **不存在** |
| 12 条打包硬约束 | 不再适用（仅在自托管离线版时才需要） |
| 包体 180–260 MB | **8–14 MB** |
| 42 人日 | **20 人日** |

`01-逆向分析报告` 的价值转为两部分：① 解释「为什么纯壳就够」；② 若将来要做**离线版**，那 12 条硬约束仍然有效，原方案可原样复活（已归档保留）。

## 4. 桌面端选型

| 方案 | 运行时 | 包体 | 冷启 | Win10 兼容 | 成本 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **Tauri 2** | 系统 WebView2（Edge Chromium） | **6–12 MB** | <1 s | 1903+ 自带（覆盖 >95%） | 中 | **采用** |
| Electron | 自带 Chromium | 80–110 MB | 1–2 s | 全版本 | 低 | 回退方案 |
| C# + WebView2 | 系统 WebView2 | 8–20 MB | <1 s | 同上 | 中高 | 不选（跨平台差） |
| 纯 PWA 安装 | 浏览器 | 0 | — | — | 极低 | 不满足「要 exe」 |

**选 Tauri 2 的三条理由**

1. 纯壳场景用不上 Electron 那 90 MB 的 Chromium；Tauri 复用系统 WebView2，包体小一个数量级，分发阻力低。
2. 构建放在 GitHub Actions，**本地不需要装 Rust 工具链**，维护成本可控。
3. 托盘、单实例、窗口状态、自动更新均有官方插件。

**回退条件**（触发即切 Electron，已写进风险表）

- WebView2 在目标用户群缺失率超预期，且引导安装体验不可接受；
- 需要 WebView2 不支持的编解码器（部分 HEVC 源）；
- 下载管理复杂度失控。

## 5. 桌面端设计

### 5.1 窗口与导航

| 场景 | 行为 |
| --- | --- |
| 启动 | 直接加载 `baseUrl`，无本地等待页 |
| 站内链接 | 窗口内跳转 |
| 站外链接（源站详情、广告等） | 交系统默认浏览器，避免壳被「绑架」 |
| `target=_blank` | 同站 → 新窗口；异站 → 系统浏览器 |
| 视频全屏 | HTML5 全屏 → 窗口全屏（Tauri 窗口 API 接管） |
| 下载 | 交系统下载器（`on_download` 钩子） |
| 关闭窗口 | 最小化到托盘（可配置为直接退出） |
| 快捷键 | `Ctrl+R` 刷新、`F11` 全屏、`Ctrl+Shift+I` 开发者工具（仅 debug） |

### 5.2 设置页（壳自绘，不依赖服务端）

- **服务器地址**：可改；改后做连通性校验（`GET /login` 返回 200/307 即视为通）。
- **清除缓存 / Cookie**：解决「更新后仍旧版」与换账号。
- **开机自启 / 关闭到托盘 / 语言**（语言可选）。
- **关于**：版本号、上游链接、许可证声明、日志目录。

### 5.3 更新机制

- 启动静默查 GitHub Release 最新 tag，有新版则在托盘/设置页提示。
- v1 采用**跳转 Release 页**的轻量方式（不自动替换），规避签名与回滚复杂度。
- v1.1 若需静默更新，再接 `tauri-plugin-updater` + 签名密钥。

### 5.4 包体预算

| 组件 | 预估 |
| --- | --- |
| Tauri 壳（Rust + 设置页前端） | 4–7 MB |
| 图标/资源 | <1 MB |
| 安装器（NSIS） | 6–12 MB |
| **合计** | **≤ 12 MB** |

## 6. Android 端设计

基于上游 `apps/android-tv` 派生（已有 WebView/GeckoView 双 flavor、leanback、遥控服务、CI 流水线），改造成手机形态。

### 6.1 改造清单

| 项 | 现状（TV 版） | 手机版改造 |
| --- | --- | --- |
| 屏幕方向 | `landscape` 锁定 | `unspecified`，竖屏优先 |
| 入口地址 | 编译期 `BuildConfig.BASE_URL` | 运行时读 `SharedPreferences`；无值进配置页 |
| 配置页 | 无 | 新增 `SetupActivity`：手输 + 校验 + 扫码导入 |
| 返回键 | 无处理 | `canGoBack()` → 返回；根页面 → 二次确认退出 |
| 下载 | 无 | `DownloadListener` → 系统下载器 + 通知 |
| 全屏播放 | 已有 `customView` | 保留，补横屏自动切换 |
| Cookie | 默认内存 | 持久化 + 退出 `flush()`，实现免二次登录 |
| 缓存 | 默认 | 提供「清除缓存」入口，处理 SW 旧版 |
| UA | `MoonTVPlusAndroidTV WebView` | `MoonTVPlusMobile/<ver>` |
| 图标/启动图 | TV banner | 自适应图标 + Splash |
| 状态栏 | 全屏沉浸 | 常规状态栏 + 播放时沉浸 |
| ABI | 默认 | `arm64-v8a` + `armeabi-v7a` |
| 签名 | CI secrets | 复用同流程，独立 keystore |

### 6.2 包体

| flavor | 体积 |
| --- | --- |
| webview（系统内核） | **8–14 MB** |
| gecko（自带内核，兼容老机型） | 60–80 MB |

v1 只发 webview 版；gecko 版等收到「老设备白屏」反馈再出。

## 7. 两端共用的契约

### 7.1 地址配置协议（供二维码 / 粘贴导入）

```json
{
  "v": 1,
  "name": "我的影视站",
  "baseUrl": "https://example.com"
}
```

- 二维码内容 = 上述 JSON（或 Base64，实现择简）。
- 桌面端设置页可「生成二维码」给手机扫，手机端「扫码导入」。
- `baseUrl` 校验：必须带协议；`http://` 允许但弹安全提示；去掉末尾 `/`。

### 7.2 UA 标识

| 端 | 追加后缀 |
| --- | --- |
| 桌面 | `MoonTVPlusDesktop/<version>` |
| Android | `MoonTVPlusMobile/<version>` |

服务端当前未使用该标识，但为将来「端特定布局」留口子。

### 7.3 登录态

- 服务端已启用 `PASSWORD`，首访 307 → `/login`。
- 客户端**不做任何登录 UI**，全交给 WebView 内的原生登录页。
- Cookie 由 WebView 持久化：
  - Tauri：WebView2 用户数据目录（`%LOCALAPPDATA%\<app>\EBWebView`）
  - Android：`CookieManager` + `flush()`
- 验收标准：**彻底关闭应用再重开，仍是登录态**。

## 8. 同步机制：为什么「零同步逻辑」

| 数据 | 存放位置 | 客户端职责 |
| --- | --- | --- |
| 播放记录 / 进度 | 服务端 kvrocks | 无 |
| 收藏 / 追番 / 订阅 | 服务端 kvrocks | 无 |
| 用户 / 权限 / 站点配置 | 服务端 kvrocks | 无 |
| 登录态 | Cookie | 持久化 |

浏览器、EXE、APK、TV 登录同一账号，记录天然一致——**因为根本不存在第二份数据**。这是远程后端方案最大的红利，也是客户端能薄到几千行的原因。

> 注意：若服务端用 `localstorage` 存储模式，数据会留在各自浏览器里，这个特性就没了。线上实例是 kvrocks，无此问题。

## 9. 安全与隐私（含一个必须处理的点）

### 9.1 域名不能硬编码进公开仓库 ⚠️

这是本方案唯一的真坑，且极易踩：

| 风险 | 后果 |
| --- | --- |
| 源码写死默认地址 | 公开仓库即公开私人站点，可能被爬、被举报、被攻击 |
| Release 产物内置地址 | 即便源码脱敏，`strings` 反编译仍可提取域名 |

**处理方案（推荐组合）**

1. **公开构建（通用版）**：仓库内**不含任何真实域名**，首启要求用户填写地址。开源友好，任何人可指向自己的实例。
2. **私有构建（自用版）**：`workflow_dispatch` + GitHub Secret `APP_BASE_URL` 注入默认地址，产物只进私有 Release 或本机留存，不公开分发。
3. 文档、示例、截图里的域名一律用 `example.com` 占位。

```yaml
# 示意：构建时注入，仓库内无明文
- run: pnpm tauri build
  env:
    VITE_APP_BASE_URL: ${{ secrets.APP_BASE_URL }}
```

### 9.2 其他安全项

| 面 | 措施 |
| --- | --- |
| 传输 | 强制 HTTPS；用户填 `http://` 时弹不安全提示但仍允许（局域网场景） |
| 证书 | 依赖系统根证书校验，**不提供「忽略证书错误」开关** |
| 外链 | 仅 `http/https` 交系统浏览器，拦截 `file://`、`intent://` 等 |
| 权限 | 摄像头 / 麦克风 / 通知按需询问，不默认放行 |
| Cookie | 不导出、不注入、不跨域共享 |
| 日志 | 不记录 URL 查询参数中的敏感字段 |

## 10. 与上游的关系

| 项 | 说明 |
| --- | --- |
| 是否修改上游 | **否**。客户端独立仓库，零 patch |
| 上游升级 | 服务端 `docker pull` 即完成，客户端通常无需发版 |
| 何时需要客户端发版 | 上游改动影响壳层行为（全屏、下载、路由结构），或需更新默认地址 |
| 许可证 | 客户端为原创代码，可自选许可；但引用上游资源（图标、文案、libbitsub）须遵守 CC BY-NC-SA 4.0 |

> 这比内嵌方案轻松很多：**不修改上游 → 不构成衍生作品**，许可证约束主要落在「引用资源 + 署名」上。但 README 仍必须保留上游署名与链接。
