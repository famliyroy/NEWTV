# 打包架构方案（APK / EXE）

> 前置阅读：`01-逆向分析报告.md`
> 本文只回答一个问题：**在不重写业务代码的前提下，怎么把这套 Next.js 全栈单体变成可安装的 EXE 与 APK。**

---

## 1. 核心判断

| 判断 | 依据 | 影响 |
| --- | --- | --- |
| 后端不可"剥离" | 251 个 API 路由 + Socket.IO 与页面同进程；代理层需绕过 CORS/Referer/SSRF 限制 | 桌面端必须内嵌完整运行时 |
| 业务代码不建议改 | 上游持续更新（v226.x 迭代快） | 采用"薄壳 + 零侵入"策略，改动限制在壳工程与构建脚本 |
| Android 端不必内嵌后端 | 内嵌需 NDK 交叉编译 better-sqlite3、工时 8–12 周且成功率低 | v1 用"壳 + 可配置服务器地址" |
| 桌面端必须内嵌 | 用户要"EXE 软件"，双击即用，不能要求先装 Docker | Electron + Node sidecar |

一句话方案：

```
一份上游代码  →  两个构建产物
  EXE = Electron 壳 + 内嵌 Node 运行时 + Next standalone（真离线）
  APK = 原生壳 + 远端/局域网 MoonTVPlus 服务（不自带后端）
```

## 3. Windows EXE 方案

### 3.1 三种引擎方案对比

| 方案 | 引擎承载 | 原生模块 | 冷启动 | 包体 | 实现难度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. Electron + 独立 Node sidecar** | 自带 `node.exe` 跑 `start.js` | 用官方 prebuilt，**零改造** | 2–5 s | 180–260 MB | 低 | **推荐** |
| B. Electron 内置 Node（`ELECTRON_RUN_AS_NODE`） | Electron 的 Node | 必须 `electron-rebuild` 重编 better-sqlite3 | 2–4 s | 150–220 MB | 中（ABI 坑多） | 备选 |
| C. Tauri 2 + Node sidecar | 同 A，壳换成 WebView2 | 同 A | 1.5–3 s | 120–180 MB | 中高（需 Rust + 侧车签名） | 二期可评估 |
| D. 纯 WebView 壳 | 无引擎，连远程 | 不涉及 | <1 s | 5–10 MB | 极低 | 降级方案 |

**推荐 A 的理由**：`better-sqlite3`、`@libsql/client`、`sharp` 都是原生模块，方案 B 每次升级 Electron 大版本都要重编并验证 `NODE_MODULE_VERSION`；方案 A 把 Node 版本锁死在自己手里，CI 可复现，升级只换 `node.exe`。

### 3.2 进程模型

```
MoonTVPlus.exe
│
├─ [Main] Electron 主进程
│   ├─ 单实例锁（second-instance → 聚焦已有窗口）
│   ├─ 端口分配：3000 → 3001…39999（bind 探测）
│   ├─ 配置中心：%APPDATA%\MoonTVPlus\config.json
│   │    { port, username, password, storage:"d1", firstRun, lang, closeToTray }
│   ├─ 启动引擎：spawn resources\runtime\node.exe start.js
│   │    cwd    = resources\app-runtime
│   │    env    = 见 3.3
│   ├─ 健康检查：GET /api/server-config（最多 40 次 × 500ms）
│   ├─ 窗口：BrowserWindow → loadURL(http://127.0.0.1:{port}/)
│   ├─ 托盘 / 关闭最小化 / 开机自启（可选）
│   └─ 退出：SIGTERM → 5s 超时 → taskkill /T /F
│
├─ [Engine] node.exe start.js（独立进程，独立崩溃域）
│   └─ Socket.IO · Next handler · SQLite（WAL）
│
└─ [Renderer] Chromium（WebGPU 可用，127.0.0.1 属安全上下文）
```

**为什么引擎要独立进程而不是 fork 进主进程**：
- 引擎崩溃不带走 UI，可从托盘"重启服务"；
- Node 版本与 Electron 解耦，避免 ABI 绑定；
- 便于在设置页展示引擎日志。

### 3.3 引擎环境变量（打包时强制注入）

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `NODE_ENV` | `production` | 必填 |
| `HOSTNAME` | `127.0.0.1` | **不得 0.0.0.0** |
| `PORT` | 动态端口 | 与主进程一致 |
| `NEXT_PUBLIC_STORAGE_TYPE` | `d1` | 走本地 SQLite |
| `SQLITE_DB_PATH` | `%APPDATA%\MoonTVPlus\data\moontv.db` | 可写目录 |
| `OFFLINE_DOWNLOAD_DIR` | `%USERPROFILE%\Videos\MoonTVPlus` | 可配置 |
| `USERNAME` / `PASSWORD` | 首启生成（16 位随机） | 空值会导致全站跳 `/warning` |
| `DOCKER_ENV` | `true` | 复用容器的等价启动路径 |
| `ENABLE_TV_MODE` | `true` | 保留 /tv |
| `NEXT_PUBLIC_SITE_NAME` | `MoonTVPlus` | 可改 |
| `BUILD_TARGET` | `desktop` | **新增**，用于构建期关闭 PWA |

### 3.4 安装包目录布局（NSIS / electron-builder）

```
MoonTVPlus\
├─ MoonTVPlus.exe
├─ resources\
│   ├─ app.asar                 # Electron 壳代码（体积 < 2 MB）
│   ├─ runtime\
│   │   ├─ node.exe             # 官方 Node 20/22 LTS（约 80–110 MB）
│   │   └─ node_modules\        # 生产依赖（better-sqlite3 已含 .node）
│   ├─ app-runtime\             # Next standalone
│   │   ├─ server.js            # ← 用上游根 server.js 覆盖
│   │   ├─ start.js
│   │   ├─ .next\
│   │   │   ├─ server\
│   │   │   └─ static\          # ← 手动拷贝
│   │   ├─ public\              # ← 手动拷贝（含 libbitsub、sw.js）
│   │   ├─ migrations\          # ← 手动拷贝
│   │   └─ scripts\             # init-sqlite.js 等
│   └─ icon.ico
└─ uninstall.exe
```

> `resources/app-runtime` 与 `resources/runtime` 分开的原因：`node_modules` 里既有壳依赖也有引擎依赖，混在一起会被 Next 的 NFT 追踪干扰。

### 3.5 首启向导（4 步）

1. **欢迎页**：说明"本软件仅提供聚合检索能力，不含任何内容源"。
2. **初始化**：生成 `USERNAME/PASSWORD`，写入配置与 SQLite，显示进度（建库 + 12 个迁移）。
3. **数据源**：可选粘贴配置 JSON / 订阅 URL（`CONFIG_SUBSCRIPTION_URL`），或"稍后在管理后台配置"。
4. **完成**：展示访问地址与本地端口，进入主界面。

跳过向导也不崩：所有步骤幂等，缺失项在管理后台可补。

### 3.6 更新机制

- `electron-updater` + GitHub Release（`latest.yml` + `.exe`）；
- 更新通道：`stable` / `beta`（对应 Release 预发布标记）；
- 引擎更新与应用更新**同包发布**，不做热更（避免 standalone 文件树不一致）；
- 失败回滚：保留上一版本 `app-runtime`，启动异常自动回退（P2）。

### 3.7 包体控制（目标 < 200 MB，硬上限 260 MB）

| 手段 | 预期收益 |
| --- | --- |
| `pnpm deploy --prod` 后删除 `*.map`、`@types`、`test` | −15–30 MB |
| 未启用的后端整包移除（postgres / upstash / turso / redis / kvrocks） | −20–40 MB |
| `sharp` **保留**（cron 路由依赖 libvips 处理海报），仅裁剪其 `@img/sharp-*` 非 win32-x64 平台包 | −5–8 MB |
| NSIS 用 LZMA solid 压缩 | 安装包再降 30–40% |
| `node.exe` 不强求裁剪（UPX 易触发杀软误报） | — |

> 实测基线需在 M1 阶段产出（见 03 文档 T-1.4），上表是经验估算，不作为承诺值。

## 4. Android APK 方案

### 4.1 定位选择（必须先决策）

| 路线 | 后端来源 | 体积 | 离线 | 工时 | 风险 |
| --- | --- | --- | --- | --- | --- |
| **A. 壳 + 可配置地址（推荐 v1）** | 用户自建（NAS/Docker/云主机）或局域网 PC 版 EXE | 8–20 MB | 否 | 1.5–2 周 | 低 |
| B. 内嵌 Node（nodejs-mobile） | 本地 | 180–300 MB | 是 | 8–12 周 | **高，不承诺** |
| C. TWA（PWA 包装） | 远程 HTTPS | 3–5 MB | 否 | 3–5 天 | 中（需域名 + DAL） |

推荐 A。理由：手机端真正缺的是"能装、能全屏、能返回、能投屏"，而不是"本地跑一个 Node"；B 的投入产出比极差，且 Android 后台进程管理会让常驻 Node 变成耗电地狱。

若一定要"APK 也能离线"，建议做成 **A + 局域网发现**：手机与 PC 在同一 Wi-Fi 时自动发现 `MoonTVPlus.exe` 实例（mDNS / UDP 广播），体验接近离线。

### 4.2 壳工程改造清单（基于 `apps/android-tv`）

| 项 | 现状 | 改造 |
| --- | --- | --- |
| 屏幕方向 | `landscape` 锁定 | `unspecified`，竖屏为主；`/tv` 路由仍可横屏 |
| 入口 URL | 编译期 `BuildConfig.BASE_URL` | 运行时 `SharedPreferences` 读取，首次进入配置页 |
| 配置页 | 无 | 新增 `SetupActivity`：手输地址 / 粘贴配置串 / 扫码 / 局域网发现 |
| 配置导入 | 无 | 二维码 payload：`{"v":1,"baseUrl":"http://192.168.1.10:3000","name":"家里"}` |
| 返回键 | 全屏无处理 | `canGoBack()` → `goBack()`；根页面 → 二次确认退出 |
| 下载 | 未处理 | `DownloadListener` → 系统下载管理器 + 通知 |
| 全屏播放 | 有 `customView` 支持 | 保留，补 PiP（Android 8+，P2） |
| Service Worker | 未处理 | 首次加载后清理 SW 缓存，避免"更新后仍旧版" |
| UA | 追加 `...AndroidTV WebView` | 追加 `MoonTVPlusMobile/<ver>`，便于服务端识别端型 |
| 图标/启动图 | TV banner | 自适应图标 + 启动 Splash |
| 明暗/状态栏 | 全屏沉浸 | 常规状态栏 + 沉浸式播放 |
| ABI | 默认 | `arm64-v8a` + `armeabi-v7a`，GeckoView 仅 arm64 |
| 签名 | CI secrets | 独立 keystore，密码进 GitHub Secrets，**不进仓库** |

### 4.3 APK 体积预算

| 组件 | webview flavor | gecko flavor |
| --- | --- | --- |
| 壳代码 + 资源 | 3–6 MB | 4–7 MB |
| GeckoView | 0 | 50–70 MB |
| 合计（release，启用 R8/资源压缩） | **8–14 MB** | **60–80 MB** |

### 4.4 与服务端的契约

壳不做业务逻辑，只提供三件事：**地址、返回、全屏**。因此需要上游配合的最小改动（可避免改上游）：

| 需求 | 无侵入做法 |
| --- | --- |
| 识别端型 | 服务端读 `User-Agent` 关键字 `MoonTVPlusMobile` |
| 配置页跳转 | 壳内本地 `about:blank` 拦截，或直接内置一个原生设置页 |
| 退出确认 | 原生 `AlertDialog`，与 H5 无关 |
| 更新提示 | 上游已有 `VersionCheckProvider` / `UpdateNotification`，可直接复用 |

## 5. 代码组织：薄壳 + 上游可同步

```
MoonTVPlus-MultiPlatform/
├─ upstream/                 # git submodule → mtvpls/MoonTVPlus（锁定 tag）
├─ shells/
│   ├─ desktop/
│   │   ├─ src/main/         # main.ts / engine.ts / config.ts / tray.ts
│   │   ├─ src/preload/
│   │   ├─ src/renderer/     # splash、setup wizard、settings、log viewer
│   │   ├─ electron-builder.yml
│   │   └─ package.json
│   └─ android/
│       ├─ app/src/main/     # 复用 apps/android-tv 结构
│       ├─ app/src/phone/    # 新增 flavor
│       └─ build.gradle.kts
├─ scripts/
│   ├─ assemble-runtime.mjs  # 从 standalone 产出 app-runtime（含 12 条硬约束校验）
│   ├─ prune-runtime.mjs     # 裁剪未用后端与 map
│   └─ verify-bundle.mjs     # 打包后自检（文件清单 + 关键文件存在性）
├─ docs/
└─ .github/workflows/
    ├─ build-desktop.yml
    ├─ build-android.yml
    └─ release.yml
```

**同步策略**：`upstream` 锁 tag（当前 `v226.1.0`），每月评估一次上游新版本；只允许在 `scripts/` 与 `shells/` 内改动，上游文件改动必须走 patch 文件（`patches/*.patch`）并在文档记录原因。这样上游更新时冲突可控。

## 6. 安全设计

| 面 | 措施 |
| --- | --- |
| 本地端口暴露 | 仅绑 `127.0.0.1`；启动时校验 bind 地址 |
| 本机其他程序调用 API | Electron `session.webRequest` 注入随机 `X-MTVP-Client` 头 + 主进程校验，阻断非壳进程 |
| Cookie | `SameSite=Lax` + `HttpOnly` 保持上游策略 |
| 密码 | 首启随机生成，存 `config.json`（600 权限），不写日志 |
| 引擎日志脱敏 | 过滤含 `PASSWORD` / `TOKEN` / `Authorization` 的行 |
| 传输 | 本地回环；Android 端局域网 HTTP 明文已在 `network_security_config` 限定 |
| 供应链 | 依赖锁版本（`pnpm-lock.yaml` 随包），CI 校验 `upstream` 提交哈希 |

## 7. 需要主人拍板的 5 个决策点

| # | 决策 | 选项 | 推荐 | 影响 |
| --- | --- | --- | --- | --- |
| D1 | APK 是否必须离线自包含 | ① 壳+地址　② 内嵌 Node | **①** | 决定 APK 是 2 周还是 10 周 |
| D2 | EXE 引擎 | ① Electron+sidecar　② Electron 内置 Node　③ Tauri | **①** | 影响 ABI 风险与包体 40 MB |
| D3 | 发布仓库 | ① 独立新仓　② fork 上游同仓 | **①** | 影响许可合规与上游同步 |
| D4 | 许可证口径 | ① 遵 CC BY-NC-SA 4.0　② 联系上游确认 MIT | **①（保守）** | 决定能否商业化/带广告 |
| D5 | 是否内置数据源 | ① 不内置，用户自填　② 内置示例源 | **①** | 直接影响合规风险等级 |

> D4、D5 不是技术问题，但会终止整个项目——建议在写第一行代码前确认。
