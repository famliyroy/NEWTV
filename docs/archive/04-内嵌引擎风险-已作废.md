## 二、技术与法务交叉风险（**必须先处理**）

### R-LEGAL-1 许可证冲突（P0）

事实核对：

| 来源 | 声明 |
| --- | --- |
| 仓库根 `LICENSE` 文件正文 | **Attribution-NonCommercial-ShareAlike 4.0 International（CC BY-NC-SA 4.0）** |
| `README.md` 的 License 章节 | `[MIT](LICENSE) © 2025 MoonTV & Contributors` |

两者互斥。以文件正文为准时的实际含义：

| 条款 | 对打包分发的影响 |
| --- | --- |
| **BY**（署名） | 必须保留原作者署名与许可声明，衍生作品需注明修改 |
| **NC**（非商业） | **不得用于商业目的**：禁止卖安装包、禁止内置广告/导流、禁止以"会员/打赏"形式变现 |
| **SA**（相同方式共享） | 你的壳层与修改**必须以相同协议发布**，不能改成 MIT 或闭源 |

**建议动作（择一，写入 `docs/adr/0001-license.md`）**：

1. **保守路径（推荐）**：按 CC BY-NC-SA 4.0 执行。仓库根放 LICENSE（原文）+ NOTICE（署名 + 修改说明），README 顶部显著声明，全程非商业。
2. **澄清路径**：向上游提 Issue 请其确认 README 的 MIT 是否为真实意图。**在得到书面澄清前，按最严格的一方执行**（即 CC BY-NC-SA）。
3. **规避路径**：不二次分发整个项目，只发布"壳工程 + 构建脚本"，让使用者自行构建。风险最低，但用户体验最差。

> 注：本文只做技术性风险提示，不构成法律意见。涉及实际发布与商业安排时，应以专业法律意见为准。

### R-LEGAL-2 内容与分发合规（P0）

上游 README 已写明：项目本身是**空壳**，"无内置播放源和直播源，需要自行收集"，并明确"请勿将实例链接公开分享或传播"。

打包分发会放大风险，因为安装包把"工具"变成了"开箱即用的应用"。因此建议以下红线：

| 红线 | 具体要求 |
| --- | --- |
| 不内置任何数据源 | 安装包内不含 `api_site`、不含 m3u 直播源、不含示例站点；首启必须为空 |
| 不放演示站点 | README 不提供任何可访问的演示实例或公共源地址 |
| 不预置账号 | 只生成随机本地账号密码，不做默认弱口令 |
| 不引导传播 | 文档措辞避免"分享给朋友""一键看全网"这类表述 |
| 保留免责声明 | README + 首启向导 + 关于页三处均需出现 |
| 不做应用商店分发 | 不上架 Google Play / 国内应用商店（过审几无可能，且会牵连账号） |
| 遵守所在地法律 | 分发前确认所在司法辖区对"影视聚合工具"的监管要求 |

### R-LEGAL-3 第三方依赖许可（P1）

`node_modules` 中包含大量依赖，其中 `artplayer`、`hls.js`、`cheerio` 等多为 MIT，但仍需：

- 打包时生成 `THIRD-PARTY-NOTICES.txt`（可用 `license-checker`）；
- 排除 GPL/AGPL 依赖，或按传染性条款处理；
- 特别留意 `libbitsub`、`anime4k-webgpu` 的许可与再分发条件。

### R-LEGAL-4 代码签名与密钥管理（P1）

- Android keystore、Windows 签名证书**绝不能进仓库**；CI 用 Secrets（上游 `android-tv.yml` 已是此模式）。
- 一旦 keystore 泄露 → 他人可发布冒名更新，需立刻更换 applicationId 或吊销。
- 文档 `docs/signing.md` 只写流程与变量名，不写任何密钥值。

## 三、项目执行风险

| ID | 风险 | 等级 | 缓解 |
